# AI 增强型项目管理平台 — 产品设计文档

## 1. 产品定位

**一个好用的项目管理工具，AI 让每个人更高效。**

不是"AI 替代人管理项目"，而是人驱动项目管理流程，AI 作为效率加速器在关键节点提供辅助——帮你生成草案、帮你发现风险、帮你整理信息、帮你写周报。所有决策由人做出，所有关键操作由人发起和确认。

**目标用户：** 中型公司（50-200 人），以 PM/Team Lead 为核心，同时服务执行者和管理者。

**管理项目类型：** 软件开发类 + 事务类（活动/审批/客户运营）。

**核心原则：**
- **独立可用：** 关掉所有 AI 功能，产品能力不低于 Teambition / 飞书项目管理 的核心功能水平
- **人控 AI：** AI 是建议者，不是决策者；人发起一切关键操作
- **渐进增强：** AI 从"帮你看"到"帮你做"，组织可按节奏采纳
- **项目宪法（OpenSpec）：** 每个项目有其独特的规范与工作方式。OpenSpec 是项目的"AI 宪法"——约定代码规范、PR 流程、风险阈值、文档模板等。AI 的行为受项目 OpenSpec 约束，确保每次输出都符合项目标准，而非给出通用答案。记忆系统告诉 AI"过去发生了什么"，OpenSpec 告诉 AI"现在应该怎么做"

## 2. 功能架构：基础 PM 层 + AI 增强层

```
┌──────────────────────────────────────────────────────┐
│                  AI 增强层                           │
│  AI 辅助执行 · 智能简报 · 风险预警 · 知识整理 · 周报  │
│  ┌────────────────────────────────────────────────┐  │
│  │           基础 PM 层（独立可用）                │  │
│  │  工作空间 · 任务管理 · 看板 · 甘特图 · 报表    │  │
│  │  知识库 · 权限 · 成员管理 · 企微通知           │  │
│  └────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

两层之间是清晰的能力边界：基础层不依赖 AI 即可独立运行，增强层调用基础层数据提供智能能力。

### 2.1 基础 PM 层（Phase 1-2）

| 模块 | 能力 | 说明 |
|------|------|------|
| 工作空间 | 创建/归档/配置 | 统一容器，容纳项目+知识库+成员+任务 |
| 任务系统 | Epic/Story/Task/Bug 四级 | 固定状态机（Todo → In Progress → In Review → Done） |
| 任务看板 | 看板/列表/甘特图 | 标准三视图切换，甘特图支持时间规划、里程碑标记、依赖可视化 |
| 任务依赖 | 阻塞/前置/关联 | 任务间依赖关系管理，支持依赖链追溯和冲突检测 |
| 批量操作 | 批量改状态/分配/优先级 | 多选任务后一键批量操作 |
| 知识库 | Markdown 编辑 + 文件上传 | Git 版本化管理，支持历史回溯。含 OpenSpec 特殊目录（项目宪法） |
| OpenSpec | 项目行为规范系统 | 创建工作空间时自动初始化，定义代码规范/PR流程/风险阈值/AI行为约束 |
| 成员管理 | 邀请/角色/移除 | 系统角色（SUPER_ADMIN/ADMIN/MEMBER）+ 工作空间角色（Owner/Manager/Member/Viewer） |
| 权限 | 3 级 RBAC | 系统角色 → 工作空间角色 → 数据范围 |
| 认证 | 密码 + 企微 OAuth（首发） | 使用 AuthProvider 接口抽象，企微为首个实现。LDAP 延后至 V1.2，后续可扩展飞书/钉钉 OAuth |
| 通知 | 站内 + 推送（企微首发） | 任务分配/状态变更/到期提醒。通知渠道使用接口抽象（NotifyProvider），企微为首个实现，后续可扩展飞书/钉钉/邮件 |
| 报表 | 项目进度/团队负载/任务分布 | 基础统计报表，数据可视化 |

### 2.2 AI 增强层（Phase 3-4）

| 能力 | 触发方式 | 说明 |
|------|---------|------|
| AI 辅助执行 | 人将任务指派给 AI Agent | Agent 生成草案 → 人 Review → 确认或打回 |
| 智能简报 | 人触发或定时（每日 8:00） | 今日值得关注的事项摘要 |
| 风险预警 | 自动扫描 | AI 标记延期/阻塞/异常状态的任务 |
| 周报生成 | 人触发 | AI 生成本周周报草稿，人浏览、微调、发出 |
| 知识整理 | 人触发 | AI 对上传文档自动分类、提取要点、生成摘要 |

## 3. 核心价值模型：人驱动流程，AI 在关键节点提效

保留五断点框架，但角色反转——**人驱动，AI 加速**：

```
想法 ────→ 计划 ────→ 执行 ────→ 追踪 ────→ 沉淀
  │          │          │          │          │
  │ AI       │ AI       │ AI       │ AI       │ AI
  │ 辅助展开 │ 推荐模板 │ 生成草案 │ 标记风险 │ 记录决策
  │ 评估工作量│ 检查完整性│ 执行日志 │ 生成简报 │ 整理经验
  │          │          │ 可见     │ 周报草稿 │
  │          │          │          │          │
  ▼          ▼          ▼          ▼          ▼
 人创建     人分配     人主导     人决策     人总结
 任务       任务       流程       处理       沉淀
```

| 阶段 | 人做什么（必须） | AI 做什么（辅助，可选） |
|------|----------------|----------------------|
| 想法→计划 | 创建任务、定义目标、确定优先级 | 辅助展开描述、推荐历史模板、初步评估工作量 |
| 计划→执行 | 分配任务给人员或 AI Agent、协调依赖、推动流程 | 若指派给 AI：生成草案（PRD/代码/设计稿），执行过程全程可见 |
| 执行→追踪 | 查看进度、处理异常、协调资源 | 扫描全项目状态、标记异常（延期/阻塞/过载）、生成简报 |
| 追踪→沉淀 | 总结复盘、记录关键经验、归档 | 辅助记录决策原因、整理经验教训、更新项目模板建议 —— **沉淀是记忆系统的数据入口，详见第 7 章** |

AI 的两种辅助模式：

1. **被动辅助（V1 默认）**：AI 在后台持续扫描，当发现值得关注的事情时推送信号。人也可以在任意时刻主动唤起 AI（Ctrl+K）提问或下达指令。
2. **主动辅助（V1.1 开启）**：人将特定任务指派给 AI Agent，Agent 生成草案放入 Review 队列。人确认后才算完成。

## 4. 产品结构

### 4.1 工作空间——平台核心容器

工作空间统一容纳项目、知识、AI、人员：

```
┌──────────── 工作空间 ────────────┐
│                                 │
│  ┌─ 项目概览 ──────────────────┐ │
│  │ 名称/目标/分类/状态/阶段    │ │
│  └────────────────────────────┘ │
│                                 │
│  ┌─ 任务看板 ──────────────────┐ │
│  │ 看板/列表/甘特图三视图      │ │
│  │ Epic → Story → Task → Bug   │ │
│  │ 待办 · 进行中 · 待Review · 完成 │
│  └────────────────────────────┘ │
│                                 │
│  ┌─ 知识库（Git 版本化）───────┐ │
│  │ Markdown 编辑/文件上传/预览  │ │
│  │ 版本回溯/历史对比(diff)      │ │
│  │ PRD/设计稿/合同/标书/会议纪要│ │
│  │ 📁 .openspec/（项目宪法）    │ │
│  └────────────────────────────┘ │
│                                 │
│  ┌─ 成员 ──────────────────────┐ │
│  │ 人类成员（Owner/Manager/    │ │
│  │ Member/Viewer）              │ │
│  │ AI Agent 助手（可指派任务，详见第 6 节）│ │
│  └────────────────────────────┘ │
│                                 │
│  ┌─ 报表 ──────────────────────┐ │
│  │ 项目进度/团队负载/任务分布   │ │
│  └────────────────────────────┘ │
└─────────────────────────────────┘
```

### 4.2 创建工作空间

- **从模板创建**：标准项目模板，一键初始化（任务结构 + 知识库目录 + OpenSpec + 成员预设）
- **空白创建**：自由配置，自动初始化最小 OpenSpec

### 4.3 OpenSpec — 项目的"AI 宪法"

#### 4.3.1 为什么需要 OpenSpec

当前设计的核心矛盾：**AI 的能力是通用的，但每个项目的规范、风格、工作方式是独特的**。

记忆系统（第 7 章）记录"过去发生了什么"——谁做了什么决定、任务如何推进、Agent 被打回了什么。但记忆是**事后的**：它只在事情发生后总结，无法在 AI 行动前提供约束。

OpenSpec 解决的是**事前约定**：在 AI 执行任何操作前，先加载项目的行为规范，告诉它"在这个项目里应该怎么做"。

```
记忆系统（事后记录）          OpenSpec（事前约定）
─────────────────────      ─────────────────────
记录：王五上次 PR 被打回      约定：PR 必须包含测试 + 截图
记录：M3 延期了              约定：延期 > 3 天自动升级为风险信号
记录：用了 React 18          约定：本项目使用 React 18 + TypeScript strict
事后总结                     事前规范
```

两者互补：**记忆告诉 AI 过去发生了什么，OpenSpec 告诉 AI 现在应该怎么做**。

#### 4.3.2 OpenSpec 目录结构

```
工作空间
└── .openspec/                     # Git 版本化，知识库的特殊目录
    ├── conventions.md             # 代码规范：命名、分支策略、测试标准
    ├── workflow.md                # 工作流：PR 流程、Review 标准、发布流程
    ├── agents.md                  # AI Agent 行为约束：各 Agent 角色的具体规则
    ├── signals.md                 # 风险信号：自定义风险阈值、通知规则、升级策略
    ├── templates/                 # 产出物模板
    │   ├── prd.md                 # PRD 文档模板
    │   ├── design.md              # 设计稿说明模板
    │   └── weekly-report.md       # 周报模板
    └── glossary.md                # 项目术语表：业务专有名词 → 解释
```

#### 4.3.3 OpenSpec 的生命周期

```
创建工作空间
    │
    ├── 从模板创建 → 使用模板自带的 OpenSpec（如"标准软件开发"模板）
    └── 空白创建 → 自动初始化最小 OpenSpec（仅 conventions.md + agents.md）
           │
           ▼
   项目管理员可在知识库中编辑 OpenSpec（Git 版本化，修改留痕）
           │
           ▼
   每次 AI 调用时，OpenSpec 核心内容注入 System Prompt
   （内容稳定、低频变更，天然适合 prompt caching）
           │
           ▼
   AI 输出受 OpenSpec 约束：PRD 按模板生成 / 风险按阈值判断 / 代码按规范检查
```

#### 4.3.4 OpenSpec 对 AI 行为的具体影响

| 场景 | 没有 OpenSpec | 有 OpenSpec |
|------|-------------|------------|
| AI 生成 PRD | 通用格式，可能不符合团队习惯 | 按 `templates/prd.md` 模板结构生成 |
| AI 扫描风险 | 只看系统内置规则（延期/阻塞） | 同时检查 `signals.md` 中自定义规则（如"负责人 3 天未更新任务"） |
| AI Review 代码 | 通用 Review 建议 | 对照 `conventions.md` 检查命名、结构、测试覆盖 |
| AI 写周报 | 自由格式 | 按 `templates/weekly-report.md` 结构输出，匹配团队汇报习惯 |
| 新人加入项目 | 需要口头传递规范 | OpenSpec 即项目"宪法"，AI 和人共同遵守同一套规则 |
| 跨项目一致性 | AI 在不同项目表现参差不齐 | 每个项目有自己的 OpenSpec，AI 行为随项目切换自动适配 |

#### 4.3.5 OpenSpec 与记忆系统的关系

```
┌──────────────────────────────────────────────────┐
│                AI 调用上下文                       │
│                                                   │
│  ┌──────────┐  ┌──────────┐  ┌───────────────┐  │
│  │ System   │  │ OpenSpec │  │ 热记忆（摘要） │  │
│  │ Prompt   │  │ 项目规范  │  │ 当前状态+决策  │  │
│  │ ~1,000   │  │ ~800     │  │ ~1,200        │  │
│  │ tokens   │  │ tokens   │  │ tokens         │  │
│  └──────────┘  └──────────┘  └───────────────┘  │
│                                                   │
│  OpenSpec 定义行为边界，记忆提供历史上下文          │
│  二者独立管理、各自演进、互不依赖                   │
└──────────────────────────────────────────────────┘
```

- **OpenSpec 是规范层**：变化频率低（周/月级别），内容精炼，所有人+AI 共同遵守
- **记忆系统是数据层**：变化频率高（日/小时级别），自动生成摘要，仅供 AI 调用
- **知识库是权威数据源**：存原始文档和最终产出物，OpenSpec 本身也存储在知识库中

#### 4.3.6 MVP 阶段实施

- [ ] 工作空间创建时自动初始化默认 OpenSpec（标准软件开发模板）
- [ ] OpenSpec 文件以知识库特殊目录形式存储（`.openspec/`），Git 版本化
- [ ] 项目管理员可在知识库中编辑 OpenSpec 文件
- [ ] AI 调用时加载当前工作空间的 OpenSpec 核心内容

**延后至 V1.1：**
- [ ] OpenSpec 模板库：按项目类型（软件开发 / 事务类 / 运营类）提供不同初始配置
- [ ] OpenSpec 内容自动注入 AI System Prompt（V1 手动维护，V1.1 自动注入）
- [ ] OpenSpec 变更时自动通知相关人员 Review

### 5.1 全局元素

- **顶部信号条**（可配置开关）：展示最近 3 条高优先级实时信号，已读/已处理的信号自动移出。超出 3 条时按优先级和时间排序。每 30 分钟刷新一次。
- **AI 对话入口**：Ctrl+K 全局唤起，上下文自动关联当前所在页面
- **投屏模式**：项目脉搏一键切换到深色投屏主题，用于站会/周会

## 6. AI Agent 设计（基于 Hermes Agent）

### 6.1 定位：智能助手，不是自主执行体

AI Agent 是人类的助手——**人分配任务给 Agent，Agent 生成草案，人确认结果**。Agent 不会主动认领任务，不会自主决策，不会绕过人类直接操作项目。

**技术基座：** 基于 Hermes Agent（Nous Research）实现，复用其自学习 Skill 闭环、四层记忆系统、MCP 兼容工具系统和多模型网关能力，避免从零构建 Agent 基础设施。

### 6.2 Hermes 与 FastAPI 协作模式

Hermes Agent 作为独立进程运行，FastAPI 通过 HTTP API 调度：

| 交互方式 | 场景 | 说明 |
|---------|------|------|
| 同步调用 | 简单查询、摘要生成 | FastAPI 等待 Hermes 返回 |
| 异步调用 | 长任务（PRD 生成、代码起草） | Hermes 执行，完成后 Webhook 回调 FastAPI |
| Webhook 回调 | Agent 产出就绪 | Hermes → FastAPI → 写入 Review 队列 → 推送通知 |

```
FastAPI                                Hermes Agent
───────                                ────────────
POST /api/workspaces/{id}/ai/run     → 创建 Agent 任务，返回 task_id
GET  /api/workspaces/{id}/ai/status  → 查询 Agent 执行状态
POST /api/workspaces/{id}/ai/review  → 提交 Review 结果（通过/打回）
                                      ← Webhook 回调通知（Agent 产出就绪）
```

> **内网部署说明：** FastAPI 和 Hermes Agent 各自 Docker 容器化，通过 docker-compose 编排。Hermes 通过 Ollama / OpenAI 兼容接口连接内网本地 LLM（DeepSeek/Qwen）。若内网网络策略复杂，可降级为 FastAPI 定时轮询 Hermes 任务状态，替代 Webhook 回调。

### 6.3 四个 Agent 角色 → Hermes Agent

沿用原设计的 4 个 Agent 角色，Hermes 通过 Skill 文件定义各角色的行为模式：

| Agent 角色 | 擅长任务 | 绑定工具集 | 产出物 |
|-----------|---------|-----------|--------|
| 需求分析师 | 需求分析 | wiki_search、术语表查询 | PRD 草案、用户故事、验收标准 |
| 设计师 | 设计任务 | 组件库查询、布局模板 | 原型草图描述、交互流程 |
| 开发工程师 | 开发任务 | 代码生成、sandbox_exec、Git 操作 | 代码草案、Bug 修复建议 |
| 项目经理 | 跟踪/报告 | task_query、风险计算、报表聚合 | 日报、周报草案、风险分析 |

### 6.4 Agent 实例化上下文

每个 Agent 实例化时注入三层上下文：

| 上下文层 | 内容 | 来源 | tokens |
|---------|------|------|--------|
| System Prompt | 角色定义 + 通用行为约束 | 系统内置 | ~1,000 |
| OpenSpec | `conventions.md` + `agents.md` + `signals.md` | `.openspec/` 目录 | ~800 |
| 热记忆 | 当前项目状态摘要 + 关键决策 + 执行历史 | Hermes MEMORY.md + Session Archive (SQLite+FTS5) | ~1,500 |

### 6.5 工具调用与命令执行

基于 Hermes 的工具系统（MCP 协议兼容），Agent 通过工具调用与外部系统交互：

```
Agent 工具集
├── 知识库工具
│   ├── wiki_search(query)        → 检索 llm-wiki 编译 wiki
│   └── source_read(path)         → 读取源文档原文
├── 任务工具
│   ├── task_query(filters)       → 查询任务列表
│   ├── task_detail(id)           → 获取任务详情
│   └── task_update(id, fields)   → 更新任务（受权限控制）
├── Git 工具
│   ├── git_log(path)             → 文档变更历史
│   └── git_diff(ver_a, ver_b)    → 版本对比
├── 通知工具
│   └── send_signal(level, msg)   → 发出风险信号
└── 沙箱工具（Hermes 内置）
    └── sandbox_exec(code)        → 安全沙箱执行代码
```

工具调用受双层权限约束：
1. **Hermes 层：** 工具白名单机制，Agent 只能调用注册的工具
2. **FastAPI 层：** 工具实际执行时校验操作权限（如 task_update 需要 Manager+ 角色）

### 6.6 AI 辅助执行流程（Hermes 版）

```
人创建任务 → 人将任务指派给 AI Agent
                  ↓
FastAPI → Hermes: 创建 Agent 任务，注入上下文（OpenSpec + 记忆）
                  ↓
Agent 状态：准备中 → 分析中（检索 wiki + 记忆）→ 生成中
                  ↓ （全过程 Work-in-Public 可见）
Agent 提交产出物 → Hermes Webhook 回调 FastAPI
                  ↓
产出物进入人的 Review 队列 → 推送通知
                  ↓
            确认通过 → 任务完成，写入执行记忆 + Hermes Skills
            需要修改 → 人说明原因 → Hermes 重新生成（打回原因写入记忆）
```

### 6.7 三个辅助档位

| 档位 | 描述 | Hermes 配置 |
|------|------|-------------|
| 建议模式 | AI 只提供建议和参考 | 限制工具集为只读（wiki_search、task_query） |
| 草稿模式（默认） | AI 生成完整草案 | 完整工具集，产出物需 Review |
| 轻量辅助 | AI 只做信息整理 | 限制输出类型（摘要/分类/格式化），不调用修改工具 |

### 6.8 Work-in-Public（执行全程透明）

Hermes Agent 的执行过程全部可见：
- Agent 当前执行状态（Hermes 状态机）
- Agent 的推理日志（Thought → Action → Observation 循环）
- Agent 引用的 wiki 条目和源文档
- Agent 的中间产出物

### 6.9 失败学习

Hermes 的执行记录（含打回原因和修正历史）自动写入 Session Archive（SQLite+FTS5）。Hermes 的 Self-Improving Learning Loop 从修正中自动生成/更新 Skill 文件，后续接到同类任务时复用修正后的流程——避免重复犯同样的错误。打回记录同时进入自定义记忆系统的执行记忆。

## 7. AI 长期记忆与 Token 压缩

### 7.1 为什么这是核心架构设计

项目生命周期通常持续数月甚至数年。如果不做记忆管理：

- 任务历史、决策记录、知识库文档、对话内容会无限膨胀
- 本地 LLM 的 token 窗口有限（DeepSeek V3 约 64K tokens）
- 超出窗口后 AI 无法"记住"项目早期的重要信息
- **AI 的回答质量会随着项目推进持续下降**

记忆系统不是"锦上添花"，而是决定 AI 能否在长周期项目中持续可用的基础能力。

**与 Hermes 内置记忆的分工：** Hermes 自带四层记忆系统（MEMORY.md + Session Archive SQLite + Skills + Honcho），负责 Agent 执行级记忆。本章描述的自定义记忆系统负责**项目级记忆**——跨 Agent、跨工作空间的业务决策和项目状态，与 Hermes 内置记忆互补而非替代。

### 7.2 多层记忆架构

```
第 0 层：即时上下文（当前会话窗口内）
  └─ 当前任务详情 + 关联文档片段 + 最近对话

第 1 层：热记忆（结构化摘要，每次 AI 调用时注入）
  ├─ 项目关键决策记录（谁在什么时候决定了什么、为什么）
  ├─ 当前迭代状态摘要（进度、阻塞、风险）
  ├─ 最近 50 条重要变更（任务状态变化、文档更新、人员变动）
  └─ Agent 执行历史（最近任务的执行反馈链，含打回记录）

第 2 层：温记忆（按需检索）
  ├─ 历史任务及其解决方案
  ├─ 知识库文档索引
  ├─ 历史讨论和评论
  └─ 经验教训记录

第 3 层：冷记忆（归档，稀疏访问）
  └─ 已完成项目的完整历史（仅在明确需要时才检索）
```

### 7.3 Token 压缩策略

| 策略 | 说明 | 触发时机 | MVP |
|------|------|---------|-----|
| **人工标注 + AI 辅助** | 人在关键节点标记"记住这个"，AI 负责格式化和结构化（非全自动摘要） | 用户手动触发 | 是 |
| **滑动窗口 + 关键帧** | 只保留关键事件（决策/里程碑/异常）+ 最近 N 天的详细记录进入 prompt | 每次 AI 调用 | 是 |
| **相关性检索** | 调用 AI 前，根据当前任务的关键词/标签检索最相关的上下文 | 每次 AI 调用 | 是 |
| **用户标记** | 用户可对重要信息打"固定"标记，这些信息优先注入上下文 | 用户主动操作 | 是 |
| **分层摘要（自动）** | 每完成任务/文档更新，AI 自动生成 3 级摘要：一句话（~50 tokens）/ 段落（~200 tokens）/ 详细（~500 tokens） | 任务完成或文档变更时 | V1.1 |
| **冲突检测** | 当记忆中的信息发生变更，自动标记旧记忆为过期 | 信息变更时 | V1.1 |
| **对话摘要** | 长对话自动总结为结构化摘要，保留结论、行动项、未解决问题 | 对话轮次超过阈值（如 15 轮）时 | V1.1 |

### 7.4 Token 预算管理

每次 AI 调用的固定 token 分配方案（MVP 采用静态分配）：

```
┌──────────────────────────────────────────┐
│ System Prompt          │  ~1,000 tokens  │
│ OpenSpec（项目规范）   │    ~800 tokens  │
│ 项目摘要（热记忆）     │  ~1,200 tokens  │
│ 当前任务上下文         │  ~2,000 tokens  │
│ 相关检索结果           │  ~3,000 tokens  │
│ 对话历史（压缩后）     │  ~2,000 tokens  │
│ 输出预留               │  ~4,000 tokens  │
├──────────────────────────────────────────┤
│ 合计                   │ ~14,000 tokens  │
│ 窗口总容量 (DeepSeek)  │  64,000 tokens  │
│ 安全余量               │ ~50,000 tokens  │
└──────────────────────────────────────────┘
```

### 7.5 MVP 阶段实施

- [ ] 热记忆：项目关键决策记录 + 当前迭代状态摘要（人工手动标注关键事件，AI 辅助改写和结构化）
- [ ] OpenSpec 核心内容注入 AI 调用上下文（项目规范层，与记忆层并列）
- [ ] 人工标注的记忆条目存储，AI 辅助生成摘要（非全自动摘要——由人在关键节点标记"记住这个"，AI 负责格式化）
- [ ] 基于关键词的相关上下文检索（MySQL FULLTEXT）
- [ ] Token 预算静态分配方案（含 OpenSpec 配额）

**延后至 V1.1：** 3 级摘要自动生成 / 向量化语义检索 / 增量上下文注入 / 冲突检测与自动过期 / Token 预算动态调整 / OpenSpec 内容自动更新检测

> **设计决策：** 自动摘要质量是 AI 工程中的未解决问题。MVP 阶段采用人工标注 + AI 辅助的方案，确保记忆质量可控，同时在真实使用中收集数据，为 V1.1 的自动摘要提供训练/评估基准。

## 8. 知识库设计

### 8.1 Git 版本化管理

- 所有文档基于 Git 进行版本控制（含 `.openspec/` 特殊目录）
- 支持历史版本回溯、对比（diff）、恢复
- 文档类型：Markdown（原生编辑）、PDF/Word/图片（上传+预览）
- `.openspec/` 目录：存储项目行为规范（conventions.md / workflow.md / agents.md / signals.md / templates/），内容直接注入 AI System Prompt
- MVP 阶段用 MySQL FULLTEXT + ngram 进行关键词搜索，V1.1 引入向量化语义搜索

### 8.2 AI 与知识库的关系

- **知识库是 AI 的上下文来源**：AI 执行任务时检索相关文档
- **AI 产出物存入知识库**：PRD 草案、设计稿、报告等（经人确认后归档）
- **AI 可辅助整理**：人对上传材料触发 AI 整理——自动分类、提取要点、生成摘要
- **OpenSpec 是知识库的特殊目录**：`.openspec/` 目录存储项目行为规范，Git 版本化管理，每次 AI 调用时注入 System Prompt

**知识库与记忆系统的关系：** 知识库存原始文档和最终产出物（含 OpenSpec），是权威数据源。记忆系统（第 7 章）的温记忆层对普通文档建立摘要索引，供 AI 快速检索。OpenSpec 作为特殊内容，不经过摘要压缩直接注入 System Prompt（内容精炼、变化低频），确保 AI 行为始终受项目规范约束。

## 13. 可观测性设计

### 13.1 为什么需要

AI Agent 的调用链涉及 FastAPI → Hermes → LLM → 工具调用 → Webhook 回调，链路长、失败模式多样。没有结构化日志和 tracing，问题排查几乎不可行。

### 13.2 三层可观测性

| 层 | 工具/方式 | 范围 |
|----|---------|------|
| **结构化日志** | Python `logging` → JSON Lines | 所有 API 请求/响应、Agent 执行步骤、LLM 调用耗时、错误堆栈 |
| **Agent 执行追踪** | Hermes 原生 logging + 自定义 span | 每个 Agent 任务从创建到完成的完整生命周期（状态变化、推理循环、工具调用） |
| **关键指标** | 聚合统计（定时查询 DB + 日志） | AI 任务成功率、平均延迟、摘要质量用户评分分布、LLM token 消耗 |

### 13.3 Agent 执行日志格式

```
{
  "trace_id": "uuid",
  "agent_type": "ANALYST",
  "workspace_id": "ws_xxx",
  "task_id": "task_xxx",
  "timestamp": "2026-05-07T10:30:00Z",
  "event": "agent.react.step",
  "step": 3,
  "thought": "...",
  "action": "wiki_search",
  "action_input": {"query": "..."},
  "observation_summary": "...",
  "duration_ms": 1240
}
```

### 13.4 MVP 阶段实施

- [ ] FastAPI 全局请求日志（中间件，含 trace_id 生成和传播）
- [ ] Hermes 执行日志结构化输出（jsonl 文件）
- [ ] 关键指标面板（基础版：任务成功率 / 平均延迟 / token 消耗，通过 FastAPI 端点查询）
- [ ] 错误告警（Agent 任务失败时推送通知给对应 PM）

**延后至 V1.1：** 分布式 tracing（OpenTelemetry）、日志聚合（ELK/Loki）、Grafana 仪表盘、自动告警规则引擎
